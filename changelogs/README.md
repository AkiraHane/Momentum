# 版本与更新记录

## 版本号

格式为 `架构版本.功能版本.优化版本-发布阶段`，例如 `2.0.2-beta1`。

| 部分 | 含义 |
| --- | --- |
| 第一位 | 架构级更新。跨版本不兼容，玩法与手感可能明显变化。 |
| 第二位 | 功能级更新。可能新增物品、动作或调整已有功能，跨版本可能不兼容。手感变化通常较小，以优化为目标。 |
| 第三位 | 优化级更新。用于修复问题、改善体验及影响较小的调整；正式版之间承诺兼容。 |
| `alpha` | 实验阶段，功能、物品或动作可能在后续修改或移除，不作稳定性与兼容保证。 |
| `beta` | 测试阶段，验证覆盖不充分，不作稳定性与兼容保证；已知问题与维护范围在对应更新记录中说明。 |
| `release` | 正式阶段，完成发布所需的验证，面向常规使用。 |

更新级别按实际影响判断。客户端改动、动作调整和内部重构也需要评估影响范围。

在相同 Minecraft 版本和加载器环境下，前两位相同、仅第三位不同的正式版，需要保持存档、配置及新旧客户端与服务器混用兼容。玩家可以选择是否更新。`alpha`、`beta` 均不承担这一承诺。

## 文件组织

```text
changelogs/
├── draft/
│   └── common.md
└── 2.0.2/
    ├── common.md
    └── 1.21.1.md
```

- `draft/`：未定版本的草稿。记录已经完成的变化，影响尚不明确的内容标记待确认。
- 数字版本目录：该基础版本截至当前发布阶段的完整更新内容。
- `common.md`：各 Minecraft 版本共用的变化。
- `<Minecraft版本>.md`：对应版本专有的变化；没有专有内容时可以省略。

准备首次发布时，整理草稿、确定版本号，将 `draft/` 重命名为数字版本目录，再新建 `draft/common.md`。同一个基础版本继续发布 `beta` 或 `release` 时，持续完善已有目录，保留此前内容。

跨基础版本整理更新内容时，以最近一个 `release` 为比较起点。`beta` 的记录保留在对应版本中，其标签不作为后续版本的比较起点。

## 更新内容写法

- 每份版本更新日志按 `English`、`中文` 分区，英文在前；以中文为依据同步英文，两部分内容对应。
- 面向玩家，条目采用“简述：说明”的形式，选取值得告知玩家的变化。
- 新增功能或操作变化，说明玩家如何操作、会发生什么；已有行为优化，说明改善的场景、问题和操作感受。
- 使用玩家熟悉的词汇，减少专有名词和计算规则，保留理解变化所需的信息。
- 按玩家体验归并相关变化，同一场景的改善集中表达。
- 根据实际实现核对描述。版本级别、兼容验证等发布决策待办留在讨论中。

## 发布

`gradle.properties` 中 `mod_version` 保存前两位，`mod_build` 保存第三位，`mod_prerelease` 保存阶段。标签格式为 `v<基础版本>-<Minecraft版本>-<阶段>`，例如 `v2.0.2-26.1.2-release`。

发布工作流从标签对应的提交读取 `changelogs/<基础版本>/common.md` 和对应的 Minecraft 文件，合成本次完整说明。至少需要一份非空更新文件。发布前整理待确认事项；正式版按兼容承诺完成验证。

GitHub 将同一基础版本的文件汇总到一个 Release：

- 首次发布建立汇总标签，例如 `v2.0.2`，固定指向首次发布的提交；完整标签保留各次构建的源码。
- 每个 Minecraft 版本保留一个说明区块，发布新阶段时替换为该版本最新的完整说明，其他 Minecraft 版本的区块和历史附件继续保留。
- 只有测试版时标记预发布；首次加入正式版后转为正式状态，后续追加测试版保持正式状态。
- 页面中的 HTML 注释用于识别自动更新区块及已处理标签；手工补充的说明放在区块外。

Modrinth、CurseForge 经人工审批后接收本次构建文件及完整说明。仓库需要允许修改已发布 Release 的附件。
